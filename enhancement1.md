# Enhancement 1 - Software Design & Engineering

### _Briefly describe the artifact. What is it? When was it created?_

This artifact is a dashboard that allows the user to view information about animals in the Austin Animal Center’s database. The dashboard was created as a Python notebook (using JupyterDash) and was designed to interface with a MongoDB database via a CRUD module implemented in Python, with the database itself generated from the `aac_shelter_outcomes.csv` file. The artifact was created during March and April 2026 for the CS340 course. 

### _Justify the inclusion of the artifact in your ePortfolio…_

For the first enhancement category, Software Design and Engineering, I chose to demonstrate my proficiency with client-server architecture. The CS340 project was the best fit for this, as it already implemented separate layers for data handling and for presentation, much like a notional server and client. This provided me with a solid basis from which to construct an actual client-server application using an API that processes HTTP requests, inspired by the MVC routing implemented in another recent course.

Almost the entirety of my effort in this enhancement went to rebuilding the broad functionality of the dashboard itself. In establishing the proper project structure, the notebook file was split primarily into an HTML template file, a JavaScript file providing most of the client-side dashboard update logic, and a Python file storing Flask routes. The overall project also had to be reorganized and expanded upon with various other files to properly implement Flask architecture. The CRUD module, by comparison, was left largely intact, mainly being altered to load environment variables from a .env file instead of having them hardcoded, and to raise errors (which the new Flask API converts to HTTP responses), instead of swallowing them and returning `False/[]/0`.

### _Reflect on the process of enhancing and modifying the artifact._

When I began work on this enhancement, I had an incomplete understanding of how Dash operated within the Jupyter notebook to produce the client-facing dashboard and made a faulty assumption about where the notional client-server boundary existed in the project (specifically, that it more neatly correlated to the boundary between the notebook and CRUD module). Dash is designed to allow pure Python syntax to cover both server-side backend functionality and client-side front-end reactivity for a web app. What I didn’t yet understand was that the client-side elements were being generated server-side in Dash and then served as HTML/JS generated by Dash, and that reworking the project into a properly structured Flask app with API routes would require rebuilding the client-side reactivity in HTML/JS. 

The JavaScript portion was the most challenging; it is my least familiar of the programming languages that I will have used across all 3 enhancement categories, and it was needed to provide reactivity to three separate interactive components on the page – the table, the chart, and the map. The chart and map were relatively simple to implement, as I discovered that Dash’s implementation of these constituted a wrapper around existing public JS libraries (`Plotly.js` and `Leaflet.js`), so refactoring the Dash elements into JS was generally a straightforward translation. The table component, however, was not based on a known public library, so it had to be rebuilt in a public JS library, for which I chose Tabulator.
