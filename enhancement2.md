_Briefly describe the artifact. What is it? When was it created?_
This artifact is the Rescue Animal Service, created for the IT145 course in Spring 2025. It is a console-based Java application with four classes, including the Driver class, which contains the `main()` method and manages two collections storing rescue animals as class objects. The Driver class provides the user with a main menu, with options including intaking a new animal, reserving an existing animal, and displaying a printout of animals in the system, filtered in any of three different ways (only one of which was implemented in the original artifact). The class objects belong to the Dog and Monkey classes, which are defined as child classes of the RescueAnimal class.

_Justify the inclusion of the artifact in your ePortfolio…_
I chose this artifact for the Algorithms and Data Structures category because, as an artifact from an early/introductory class, its implementation of its methods and variables was shallow and inefficient, making them ideal choices for enhancement and optimization. In particular, the various fields of the RescueAnimal classes were almost all strings, with very little input validation, and the process of checking for duplicate entries and for unreserved animals relied on simple list iteration. 
My enhancements included converting the various fields of the RescueAnimal class and child classes into more appropriate data types (such as the acquisitionDate converted to a LocalDate object), implementing extensive input validation for the new types, and replacing the lists of each animals with pairs of hashed collections – one as a single (per-animal) HashMap optimized for the intake method’s duplicate lookup, and the other as a nested collection (a HashMap with ArrayLists as values) optimized for the reserve method’s lookup of available animals. The former allows for O(1) lookups of existing animals, while the latter maintains the need for an O(n) lookup but allows for the list of potential candidates to be immediately narrowed from the entire set of animals (of the chosen type) to animals belonging to the chosen service country (e.g., a search for available dogs in Canada can immediately filter for dogs in Canada – it must then perform an O(n) traversal of that list, but this will tend to be quicker than traversing the entire dog list).
The input validation was implemented both within the class methods for RescueAnimal and its child classes, where it was refactored to throw an error on input deemed invalid, and within the intake and reserve methods in the Driver class, where it takes advantage of helper methods to prompt for user input and check it for validity before passing anything to the class constructor methods, ensuring the objects that Driver instantiates or alters are only receiving valid data. As some string fields had a limited set of valid options, the collections defining these options were reorganized to ensure that all input validation for a field referenced the same sets of options (such as the valid monkey species, which was moved to a private, immutable class variable of the Monkey class, and obtained by the driver via a getter method). Intake prompts for fields such as these were also reworked to rely on numbered menu selections corresponding to valid values, instead of taking and validating a user-typed string input (akin to the main menu’s own functionality).

_Did you meet the course outcomes you planned to meet…_
I believe I have covered the third course outcome through my refactoring of the Dog and Monkey lists into pairs of HashMaps. These two HashMaps were designed to optimize the performance of the functions that access them, and the design of the HashMap containing a nested ArrayList was chosen after evaluating it against a similar design which would even further optimize performance (by storing only unreserved animals, and merely checking if the ArrayList contained values), but which would also be much more vulnerable to desynchronization from the other HashMap. I also demonstrated an aspect of the fourth course outcome, by eliminating “magic number” literals in favor of constants defined once and referenced by the rest of the program, and by refactoring input looping logic (for specific prompts, mostly in the intake method) into separate helper methods. I also believe my work has complemented the Category 1 artifact in covering the fifth course outcome, as my work on the artifact came to include similar typing and input validation to that which was planned for the other artifact before subsequently being postponed, mitigating the risk posed to the program by bad user input. 

_Reflect on the process of enhancing and modifying the artifact._
The main challenges I faced with this artifact were understanding and implementing unfamiliar patterns and data structures and ensuring that the input validation was sufficient without being disruptive to the user experience. One instance where these intersected was at the promptDouble() method in the driver class: I needed for the method to be able to return some kind of value that would signal to the caller (in the intake method) that the user had provided empty input and wished to return to the main menu. Since each field storing a double corresponded to a trait that had to be a positive, non-zero value (e.g. height, weight, age), I initially considered using either -1.0 or 0.0 as sentinel values. However, I then identified this as a form of magic number, and recognized that future code using the promptDouble() method may want to allow zero or negative values; thus, I familiarized myself with Java’s `Optional<>` class, which facilitates “empty” returns.  While it was not strictly necessary for the functionality of the Rescue Animal Service as-is, this change has ensured that the intake method’s escape behavior will continue to work as intended if negative values cease to be disallowed in future iterations of the program.
